# 第一阶段真实源字段与能力边界

本说明先于后续派生实现更新。依据是原始 `data/README.md`、本次本地/服务器全量文件清单与 SHA-256 校验、69 个业务目录首个真实 Parquet schema，以及关键表首尾分区和停牌事实字段检查。原始文件不修改、不覆盖、不删除；所有修正记录在项目配置和本说明。

## 实际覆盖

本地与服务器共 71 个一级目录，其中 `_meta/`、`_logs/` 是辅助数据，69 个是业务目录。两端均为 109,320 个文件、7,998,006,450 字节，逐文件 SHA-256 一致；这确认本地与服务器当前内容相同，不代表供应商数据不存在缺失或延迟。

## 公告日期与财务版本

三张 VIP 财务均实际提供 `ann_date`、`f_ann_date`、`end_date`、`report_type`、`update_flag`。`f_ann_date` 是实际公告日；供应商的报告类型区分累计合并、单季及不同调整口径，不能混在一起做差分。[TuShare 利润表字段说明](https://tushare.pro/document/2?doc_id=33)

这些字段存在真实差异：`income_vip/by_period/20180630.parquet` 中有 71 行 `ann_date != f_ann_date`，该分区 `ann_date` 最晚为 20200327，`f_ann_date` 最晚为 20250425。只使用较早的 `ann_date` 会让后来公告的记录提前可见。因此 V1 明确采用：

1. 保留两个原始日期；公告依据日为非空有效日期 `max(ann_date, f_ann_date)`。
2. 从依据日之后的下一个 SSE 交易日开始可用，公告当天不能使用。
3. `fina_indicator` 没有 `f_ann_date`，按其 `ann_date` 滞后并标注源能力；没有日期的记录不能通过报告期补一个公告日。
4. `financial_available` 保留实际源中所有报告类型、冲突和版本；单季度/TTM 仅处理配置的累计 `report_type='1'`，避免把单季口径再差分。
5. 日期超出已知交易日历或缺少后续交易日时，明确报告不可对齐，不能强行映射到最后一个交易日或凭空延展日历。

配置中的财务键是候选键，不保证真实源唯一。相同股票、报告期、公告日期的多记录或不同金额需要在画像中报告并保留可追溯标识，不能静默覆盖。当前源文件不证明供应商保存了每次修订前的完整历史快照；V1 只能对现有版本执行公告滞后。

Step 3 全量画像进一步发现，相同候选键对应不同完整记录的冲突组分别为 `balancesheet_vip=31`、`cashflow_vip=2`、`income_vip=6`。例如利润表 `002961.SZ/20250630` 的冲突记录连 `update_flag` 都相同，因此不能把该标志当作任意择一依据。`financial_available` 以完整记录哈希标识并保留源版本；同一股票、同一生效日、同一报告期和指标出现相互冲突的金额时，受影响的单季/TTM 为 `NULL`，明确标记 `ambiguous`，不按输入顺序或 `update_flag` 静默选值。

`fina_indicator` 实测有 9 条 `ann_date` 是字面字符串 `None`。这些原始记录和原始值保留，另标 `invalid_announcement`，不成为研究日可见的财务记录；不得用报告期、文件名或当前日期补造公告日。`revenue` 等金额缺失继续保持空值，不能用 0 伪装成已披露的零金额。

累计白名单为利润表 `revenue/n_income_attr_p` 与现金流量表 `n_cashflow_act`。资产负债表的 `total_assets` 是时点余额，财务指标 `eps` 是每股指标，不允许机械差分或四季求和。缺 Q2 时 Q3 不能减 Q1，缺来源季度时 TTM 留空并说明原因；首期 20180630 缺少此前 Q1，同样适用。

## 历史代码和跨市场身份

全量核验显示，**行情中的全部 `ts_code` 都能匹配当前 `stock_basic`，行情 orphan 数为 0**。但财务源中有大量不能匹配当前基础表的历史代码，尤其旧北交所代码；当前数据不足以构造带生效日期、可核验的历史换码映射。财务记录必须保留原始 `ts_code`，不能以内连接当前基础表的方式丢掉，也不能猜测其新代码。跨代码财务关联能力暂挂。

当前 `stock_basic` 中另有 97 个证券没有任何行情：96 个 `list_status=D`，以及 `list_date=20260911` 的 `688801.SH`。缺行情不等于证券不存在，基础身份仍保留，行情可用性单独表达。

北交所证券还存在早于当前 `stock_basic.list_date` 的历史报价。例如 `920017.BJ` 的 `list_date=20230531`，但 20180628–20220609 已有 679 行报价。这些数据可能反映跨市场历史，现有来源没有足够身份区间证明，不能把较早报价当成已在 A 股上市，也不能把当前北交所身份回溯到全部历史报价。处理层保留全部原始代码和价格；明确上市身份以 `stock_basic.list_date` 为起点，跨市场历史覆盖不完整的部分单独标注、暂挂。此规则不要求删除上市前价格。

## 价格、停牌与涨跌停

V1 保留原始价格，用当日原始 OHLC 乘当日 `adj_factor` 得到研究价格；不使用未来某个末日因子归一，也不覆盖原始成交价格。厂商 qfq/hfq 字段可追溯保留，不用来猜测缺失历史。`ret_1d` 只在相邻交易日均有该股行情时计算，缺行情后不能跨多个交易日计算所谓一日收益率。

`suspend_type=S` 是停牌，`R` 是复牌；`suspend_timing` 非空表示日内时段，空值表示全天情形。比如原始 20180608 的 `601138.SH` 为 `09:30-10:00`，20180612 的 `300134.SZ` 为 `13:00-15:00`。V1 可以对出现日内停牌的股票采取保守买卖限制，但必须明确原因是“日内停牌的保守规则”，不能把事实描述为全天没有成交机会。[TuShare 停复牌字段说明](https://tushare.pro/document/2?doc_id=214)

`suspension_events_complete=true` 同时限定在配置的 20180601–20260911 当前源覆盖范围和 `suspension_complete_code_suffixes=[SH,SZ]`；BJ 因历史换码缺口保留未知。依据是对应交易日日分区齐全且 SH/SZ 停复牌事件均能匹配代码；它不保证未来追加范围、供应商外部真实性或盘中准确时序。缺行情必须单独报告，不能自动变成停牌事实。

`limit_list_d.limit` 的 U、D、Z 分别表示涨停、跌停、炸板；Z 不能当作收盘涨停。该接口自 2020 年起提供，官方明确不提供 ST 股票统计，因此 `limit_events_complete=false`。有事件可以作为方向事实；未出现事件以及 2020 年前的日期不能自动断言没有触及涨跌停。[TuShare 涨跌停列表说明](https://tushare.pro/document/2?doc_id=298)

`ft_limit.up_limit/down_limit` 属于中金所期货合约，不是股票日限价。现有股票价格表也没有对应双向限价，V1 不按未经完整历史规则验证的固定百分比补造。

## 财务版本与查询约定

`financial_available` 保留四张财务表全部原字段与原始日期字符串，日期另标准化为 DATE。
完整原记录哈希为 `record_id`，重复内容合并时保留 `source_count/source_locations`。
`version` 只是同报告期的确定性序号，不是冲突记录的优先级。
`effective_ann_date=max(ann_date,f_ann_date)`；非空非法日期、无公告日、无效报告期、
公告早于报告期、公告超出日历或无后续交易日的记录不可见，并保留原因。
`financial_asof` 限制研究日处于日历覆盖，并只返回已到可用日的全部版本。
财务构建始终保留完整历史，不以行情区间的 start/end 截去差分或 TTM 所需前史。
